# Offline NuGet Validation for Codex

## Purpose

This project uses a repo-local offline NuGet feed so Codex can validate changes without relying on:

- live access to `nuget.org`
- a pre-populated global NuGet cache
- persistent package state in the execution environment

This matters because Codex validation often runs in an isolated environment with an empty package cache. In that environment, a normal `dotnet build` fails unless dependencies are already available locally.

The offline workflow makes validation reproducible and network-independent once the feed has been generated.

---

## What this setup does

The workflow has two phases:

1. **Bootstrap / refresh phase**  
   Run on a machine with internet access. This:
   - restores packages from NuGet
   - generates or updates `packages.lock.json`
   - downloads the exact locked package set into a repo-local feed

2. **Validation phase**  
   Run anywhere, including offline or inside Codex. This:
   - restores from the local feed only
   - uses the lock file to ensure deterministic package resolution
   - builds without touching the network

---

## Files involved

### `CbetaTranslator.App.csproj`

Contains:

```xml
<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
````

This causes NuGet to generate `packages.lock.json`, which records the exact resolved dependency graph.

### `packages.lock.json`

This is the source of truth for the offline dependency set.

It records, for each resolved package:

* package ID
* exact resolved version
* package type
* content hash

If package references change, this file must be regenerated.

### `NuGet.Config`

This file points restore at the repo-local feed instead of public NuGet.

Offline validation uses a config like this:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="local" value="vendor/nuget-feed" />
  </packageSources>
</configuration>
```

`<clear />` is important. It prevents accidental fallback to `nuget.org` or other machine-specific sources.

### `scripts/build-offline-feed.sh`

This script reads `packages.lock.json` and downloads the locked package set into the local feed directory.

It should be run only during bootstrap or dependency refresh.

### `vendor/nuget-feed/`

This directory contains the `.nupkg` files used for offline restore.

It is the actual offline package source.

### `vendor/nuget-feed/offline-feed-manifest.json`

This is an audit artifact generated by the feed build script. It records which locked packages were used to build the feed.

It is useful for maintenance and troubleshooting.

## Normal validation workflow

These are the commands Codex should use:

```bash
env DOTNET_CLI_HOME=/tmp dotnet restore CbetaTranslator.App.sln --locked-mode --configfile NuGet.Config
env DOTNET_CLI_HOME=/tmp dotnet build CbetaTranslator.App.sln --no-restore
```

### Why these flags matter

#### `DOTNET_CLI_HOME=/tmp`

This simulates an environment with no useful persistent NuGet state. It prevents validation from accidentally succeeding because of packages already cached on the machine.

#### `--locked-mode`

This forces restore to use the versions recorded in `packages.lock.json`.

If the project file and lock file diverge, restore fails instead of silently re-resolving packages.

#### `--configfile NuGet.Config`

This forces restore to use the repo-local package source configuration.

Without this, restore can pick up machine-specific defaults and hide problems.

#### `--no-restore`

This ensures build uses only the output of the explicit restore step.

If build fails here, the problem is no longer “restore did not happen.”

## Initial bootstrap

Run this on a machine with internet access.

### 1. Enable lock file generation

Ensure `CbetaTranslator.App.csproj` contains:

```xml
<RestorePackagesWithLockFile>true</RestorePackagesWithLockFile>
```

Recommended placement: in the main top-level `PropertyGroup`, near other build-wide settings such as `TargetFramework` and `Nullable`.

### 2. Temporarily allow online restore

For bootstrap, `NuGet.Config` must allow access to `nuget.org`.

A bootstrap version can look like this:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="nuget.org" value="https://api.nuget.org/v3/index.json" />
  </packageSources>
</configuration>
```

### 3. Generate or refresh the lock file

Run:

```bash
dotnet restore CbetaTranslator.App.sln --configfile NuGet.Config
```

This generates or updates `packages.lock.json`.

### 4. Build the offline feed

Run:

```bash
./scripts/build-offline-feed.sh
```

This downloads the exact locked package set into:

```text
vendor/nuget-feed/
```

### 5. Switch `NuGet.Config` back to offline mode

Use:

```xml
<?xml version="1.0" encoding="utf-8"?>
<configuration>
  <packageSources>
    <clear />
    <add key="local" value="vendor/nuget-feed" />
  </packageSources>
</configuration>
```

### 6. Verify the offline workflow

Run:

```bash
env DOTNET_CLI_HOME=/tmp dotnet restore CbetaTranslator.App.sln --locked-mode --configfile NuGet.Config
env DOTNET_CLI_HOME=/tmp dotnet build CbetaTranslator.App.sln --no-restore
```

If both succeed, the offline validation setup is complete.

## How the feed build script works

`scripts/build-offline-feed.sh` does the following:

1. reads `packages.lock.json`
2. extracts each locked package ID and resolved version
3. downloads each `.nupkg` into `vendor/nuget-feed`
4. writes `offline-feed-manifest.json`

The script does **not** attempt to reimplement NuGet’s internal content validation logic. Integrity is enforced by the locked restore step:

```bash
dotnet restore --locked-mode --configfile NuGet.Config
```

That is the correct validation point.

## How to update dependencies safely

Use this process whenever you:

* add a new `PackageReference`
* change a package version
* update existing dependencies
* modify package source behavior

### 1. Temporarily switch `NuGet.Config` to online bootstrap mode

Use `nuget.org` as the package source.

### 2. Regenerate the lock file

Run:

```bash
dotnet restore CbetaTranslator.App.sln --configfile NuGet.Config
```

This updates `packages.lock.json`.

### 3. Rebuild the offline feed

Run:

```bash
./scripts/build-offline-feed.sh
```

This downloads any new or changed package artifacts needed by the updated lock file.

### 4. Switch `NuGet.Config` back to offline mode

Use the local feed only.

### 5. Re-verify offline validation

Run:

```bash
env DOTNET_CLI_HOME=/tmp dotnet restore CbetaTranslator.App.sln --locked-mode --configfile NuGet.Config
env DOTNET_CLI_HOME=/tmp dotnet build CbetaTranslator.App.sln --no-restore
```

If locked restore fails, the feed is incomplete or the lock file does not match the project state.

## Expected maintenance workflow

### Most of the time

Use only the offline validation commands:

```bash
env DOTNET_CLI_HOME=/tmp dotnet restore CbetaTranslator.App.sln --locked-mode --configfile NuGet.Config
env DOTNET_CLI_HOME=/tmp dotnet build CbetaTranslator.App.sln --no-restore
```

### Only when dependencies change

Use the refresh workflow:

1. switch to online bootstrap config
2. run `dotnet restore`
3. run `./scripts/build-offline-feed.sh`
4. switch back to offline config
5. rerun locked restore and build

## Failure modes and what they mean

### `NU1101: Unable to find package ... in source(s): local`

Meaning:

* `NuGet.Config` points only to the local feed
* the local feed is missing one or more required packages

Fix:

* regenerate the lock file if dependencies changed
* rerun `./scripts/build-offline-feed.sh`
* verify the feed directory contains the required `.nupkg` files

This is not a compiler problem.

---

### Locked restore fails even though packages exist

Meaning:

* `packages.lock.json` does not match the current project references, or
* the feed contains the wrong package versions

Fix:

* temporarily switch to online bootstrap config
* rerun `dotnet restore`
* rebuild the feed
* switch back to offline config
* retest

---

### `dotnet build --no-restore` fails after locked restore succeeds

Meaning:

* dependency resolution worked
* the remaining problem is in source code, build configuration, or warnings treated as errors

Fix:

* inspect the build output as a normal compile failure
* do not troubleshoot NuGet first

---

### Restore succeeds on one machine but fails in Codex

Meaning:

* the local machine is using ambient package sources or a warm global cache
* Codex is using the intended isolated environment

Fix:

* always test with:

  * `DOTNET_CLI_HOME=/tmp`
  * `--locked-mode`
  * `--configfile NuGet.Config`

If that local test passes, Codex should have the same dependency behavior.

---

## Why `packages.lock.json` matters

Without a lock file, restore can change over time because:

* transitive dependency graphs can shift
* package source state can change
* different environments can resolve packages differently

With a lock file, the dependency closure is explicit and reproducible.

That is the foundation of this workflow.

---

## Why the local feed matters

A lock file alone is not enough for offline validation.

`packages.lock.json` tells NuGet **what** to restore.
`vendor/nuget-feed/` provides **where** to get it without network access.

You need both.

---

## Suggested repository policy

Treat these files as part of the validation system:

* `packages.lock.json`
* `NuGet.Config`
* `scripts/build-offline-feed.sh`
* `vendor/nuget-feed/`
* `vendor/nuget-feed/offline-feed-manifest.json`

If dependency changes are committed without updating the lock file and feed, offline validation will break.

## Notes

* Build warnings are separate from dependency reproducibility.
* A successful locked restore plus `--no-restore` build proves the offline dependency setup works.
* If a package version changes, the lock file and local feed must be refreshed together.

## Summary

This project uses an offline NuGet validation workflow so Codex can build deterministically without public network access.

The workflow depends on two artifacts staying in sync:

1. `packages.lock.json`
2. `vendor/nuget-feed/`

When package references change:

1. restore online
2. regenerate `packages.lock.json`
3. rebuild the feed
4. switch back to offline mode
5. retest locked restore and build

That is the full maintenance model.
